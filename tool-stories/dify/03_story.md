# ストーリー3：「契約書レビューBot」
副題 ── 中村弁護士と深夜の契約書山 ──

## 登場人物
中村 健太（41歳）。都内の中規模法律事務所に所属するシニアアソシエイト弁護士。M&A・事業提携案件を専門とし、スタートアップや中堅企業のクライアントを多数抱える。毎月20〜30本の契約書レビューをこなすが、近年は業務量増加で深夜残業が常態化していた。

## 問題
月に処理する契約書は平均25本、総ページ数は800〜1,000ページ。秘密保持契約（NDA）や業務委託契約などの定型的なレビューは「慣れた作業」だが、それでも1本あたり90分はかかっていた。事務所全体でのレビュー時間は月400時間超。パートナー弁護士からは「付加価値の低い定型作業に時間を使いすぎ」と指摘されていた。

## 出会い
法律系テックのコミュニティイベントで「DifyでRAGを使った契約書チェックBot」のデモを見た。「ハルシネーションが怖い」という懸念を持ちながらも、「あくまでドラフトのチェックリスト支援ならアリかも」と試してみることにした。

## 実装
1. **Knowledge Baseノード**：過去5年分の修正済み契約書500本と、事務所独自のレビューチェックリスト（250項目）をRAGとして登録。
2. **Document Extractor（ファイルアップロード）**：クライアントから受け取ったPDF契約書をドラッグ＆ドロップ入力。
3. **Iterationノード**：契約書をセクション（前文・定義・義務・表明保証・解除・損害賠償・管轄）ごとに分割してループ処理。
4. **LLMノード**：各セクションを事務所のチェックリストと照合し、「問題なし／要確認／要修正」の三段階で評価・コメントを生成。
5. **Codeノード**：全セクションの評価をまとめてMarkdown形式のレビューレポートを出力。

## 壁
LLMが過去の類似条項を参照して「この損害賠償上限条項は我々の過去案件では修正を求めた」という趣旨のコメントを出力した。しかし参照元の案件が機密情報を含む可能性があり、Knowledge Baseに何を入れるべきかの境界線が不明確になった。

## 解決
Knowledge Baseを「一般公開済みの契約書ひな形集・法令」と「社内チェックリストのみ」に限定し直した。クライアント案件の過去契約書はRAGから除外。「AIは条項の問題点を法的観点から指摘するが、過去案件との比較は行わない」というルールをプロンプトに明記した。

## 結果
| 指標 | Before | After |
|------|--------|-------|
| NDA・定型契約レビュー時間 | 90分/本 | 25分/本 |
| 月間レビュー処理数 | 25本 | 38本（対応可能数） |
| チェック漏れ指摘件数（QC） | 月8件 | 月2件 |
| 深夜残業（22時以降）日数 | 月18日 | 月7日 |

## 使ったDify機能
| ノード/機能 | 用途 |
|------------|------|
| Knowledge Base（RAG） | チェックリスト・ひな形集の参照 |
| Document Extractor | PDF契約書のテキスト抽出 |
| Iterationノード | セクション別ループ処理 |
| LLMノード | 各セクションの問題点指摘・評価 |
| Codeノード | レビューレポートのフォーマット整形 |

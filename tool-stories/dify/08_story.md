# ストーリー8：「深夜アラートを止めろ」
副題 ── 伊藤さんとインシデント対応の自動化 ──

## 登場人物
伊藤 翔太（34歳）。SaaS企業のSRE（Site Reliability Engineer）チームリーダー。10名のエンジニアを率いてシステムの安定稼働を担う。月に約30件発生するシステムアラートの初動対応のため、夜間・休日問わずオンコール対応が続き、チームの疲弊が限界に達していた。

## 問題
月間インシデント件数は約30件。そのうち70%は「既知のパターン」で、過去のRunbook（手順書）に対応策が書かれていた。しかし深夜にアラートが鳴るたびに担当者がRunbookを探してSlackに内容を転記し、コマンドを手動実行するという作業に20〜40分を要していた。未知の問題を要する真のインシデントは月5〜6件だったにも関わらず、チーム全員が毎晩緊張状態にあった。

## 出会い
SRE Conferenceで「DifyのWorkflowとSlack Botを組み合わせてRunbook実行を自動化している」という発表を聞いた。「人間のループをどこに入れるかが肝」というコメントが刺さり、帰社後すぐに試作を始めた。

## 実装
1. **Webhookトリガー**：監視ツール（Datadog）からのアラートWebhookをDifyが受信。
2. **LLMノード（分類）**：アラートの内容・エラーメッセージ・影響サービスを解析し、「既知パターン」か「未知インシデント」かを分類。
3. **Knowledge Baseノード**：過去200件のインシデント対応履歴とRunbook全文をRAGで登録。
4. **IF/ELSEノード**：既知パターンなら自動対応フローへ、未知なら人間エスカレーションフローへ分岐。
5. **HTTP Requestノード（既知対応）**：対応コマンドをRunbookから取得し、承認後に実行APIへ送信。PagerDutyへの自動対応ログも記録。
6. **Human Inputノード**：自動実行前に担当者のSlack承認（✅/❌）を要求するステップを挿入。
7. **LLMノード（ポストモーテム）**：対応完了後、5W1H形式のインシデントレポートのドラフトを自動生成。

## 壁
「既知パターン」と判定されたアラートでも、本番データベースへの書き込みコマンドを含むRunbookステップが自動実行フローに入ってしまい、ある日の深夜テスト中に想定外のDB操作が走ってしまった。Human Inputノードを設けていたが、テスト時に「承認ボタンを押してどうなるか見てみよう」という好奇心がミスを生んだ。

## 解決
Runbookの各ステップに「自動実行可」「要承認」「絶対手動のみ」の3段階フラグをメタデータとして付与し直した。「絶対手動のみ」フラグが含まれる場合はWorkflowが自動実行フローに入れないガードを実装。さらにステージング環境と本番環境でWorkflowを完全に分離した。

## 結果
| 指標 | Before | After |
|------|--------|-------|
| 既知インシデントの初動対応時間 | 20〜40分 | 3〜5分（承認含む） |
| 深夜対応でオンコール起床が必要な件数 | 月約21件 | 月約7件（未知のみ） |
| インシデントレポート作成時間 | 1時間/件 | 10分（ドラフト確認のみ） |
| チームのオンコール疲弊スコア（社内調査） | 7.2/10（高疲弊） | 3.8/10 |

## 使ったDify機能
| ノード/機能 | 用途 |
|------------|------|
| Webhookトリガー | Datadogアラートの受信 |
| LLMノード（分類） | 既知/未知インシデントの分類 |
| Knowledge Base（RAG） | Runbook・過去対応履歴の検索 |
| IF/ELSEノード | 自動対応/人間エスカレーションの分岐 |
| Human Inputノード | Slack承認ゲート |
| HTTP Requestノード | 実行API・PagerDuty連携 |
| LLMノード（ポストモーテム） | インシデントレポートドラフト生成 |

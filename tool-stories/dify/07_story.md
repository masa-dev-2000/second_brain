# ストーリー7：「会議を終わらせるBot」
副題 ── 鈴木部長と「誰も読まない議事録」の終焉 ──

## 登場人物
鈴木 雅彦（52歳）。上場企業の経営企画部長。毎週月曜の経営会議（役員9名・約90分）のファシリテーションを担当。会議後に若手スタッフが議事録を作成しているが、翌日の昼過ぎまで完成しないことが多く、意思決定のフォローアップが遅れることに長年悩んでいた。

## 問題
週1回の経営会議の議事録作成に、担当スタッフが平均3.5時間を費やしていた。完成が翌日昼になるため、「会議で決まったこと」がSlackで共有されるのは24時間後。決定事項への対応が遅れ、役員から「アクションが遅い」という指摘が月に数回あった。また議事録の形式が担当者によってバラバラで、「どこに何が書いてあるかわからない」という声も多かった。

## 出会い
IT部門から「音声文字起こしAPIとDifyを組み合わせると議事録自動生成ができる」と提案された。「AIに経営会議の内容を処理させることへの抵抗感」を覚えつつ、まずは議事録のみオンプレ環境のDifyで試すことにした。

## 実装
1. **Webhookトリガー**：会議録音データをWhisper APIで文字起こし後、テキストをDifyのWorkflowに送信。
2. **LLMノード（構造化抽出）**：文字起こしテキストから「議題ごとの議論内容」「決定事項」「継続検討事項」「アクション（担当者・期日）」を抽出。
3. **Codeノード**：抽出情報を社内標準テンプレートのJSON構造に変換。
4. **LLMノード（サマリー生成）**：全体のエグゼクティブサマリー（250字以内）を生成。
5. **HTTP Requestノード（Notion）**：議事録をNotion経営会議ページに自動作成・保存。
6. **HTTP Requestノード（Slack）**：アクション一覧と担当者メンションを含む要約をSlackの経営会議チャンネルに自動投稿。
7. **Scheduled Trigger**：毎週月曜15:00に前週の未完了アクションをリマインド投稿。

## 壁
役員が話す際に固有名詞・社内略語・プロジェクトコード名（「PJ-Alpha」「新中計」など）が多用され、LLMが意味を取り違えて議事録に誤解を招く要約を生成してしまった。特に「PJ-Alphaの承認」を「新規プロジェクトの一般的な承認プロセス」と解釈した事例があった。

## 解決
Knowledge Baseに「社内用語集・プロジェクト一覧・役員氏名と担当領域」を登録し、文字起こし後にまず用語正規化ノードを通すフローに変更した。固有名詞のリストをシステムプロンプトにも埋め込み、「用語集に載っていない略語は推測せずそのまま記載せよ」という指示を追加した。

## 結果
| 指標 | Before | After |
|------|--------|-------|
| 議事録完成までの時間 | 翌日昼（約20時間後） | 会議終了後30分以内 |
| スタッフの議事録作業時間 | 3.5時間/回 | 15分（確認・承認のみ） |
| 決定事項の共有タイミング | 翌日昼 | 当日中（会議後即時） |
| アクション未完了の指摘 | 月3〜5件 | 月0〜1件 |

## 使ったDify機能
| ノード/機能 | 用途 |
|------------|------|
| Webhookトリガー | 文字起こしテキストの受信 |
| LLMノード（×2） | 構造化抽出・エグゼクティブサマリー生成 |
| Codeノード | 社内テンプレートへのJSON変換 |
| HTTP Requestノード（×2） | Notionへの議事録作成・Slackへの通知 |
| Knowledge Base（RAG） | 社内用語集・プロジェクト一覧 |
| Scheduled Trigger | 毎週月曜のアクションリマインド |

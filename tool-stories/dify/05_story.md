# ストーリー5：「物件提案Botの誕生」
副題 ── 木村さんと「条件が多すぎる」お客様 ──

## 登場人物
木村 彩香（32歳）。首都圏を中心に展開する中堅不動産会社の渋谷支店スタッフ。入社6年目で成績優秀だが、問い合わせ対応の初期ヒアリングに毎日2〜3時間を費やしており、「条件整理だけで疲弊してしまう」と感じていた。特に曖昧な希望（「なんとなく広くて、駅近で、でも静かな場所」）を持つ顧客の対応が苦手だった。

## 問題
月間問い合わせ数は支店全体で約200件。そのうち「条件を絞れずに離脱する顧客」が35%を占め、初回問い合わせから内見予約までの転換率は18%にとどまっていた。物件データベースには約3,000件の登録物件があるが、担当者が手動で条件照合していたため、1顧客あたりの提案準備に平均40分かかっていた。

## 出会い
本社のDX推進部から「Difyで物件提案の自動化ができないか検証してほしい」という依頼が木村さんの支店に来た。「現場のことを一番わかっているあなたにプロトタイプを作ってみてほしい」と支店長に言われ、Difyのアカウントを渡された。

## 実装
1. **Chatflowアプリ**：LINEから問い合わせた顧客と自然な会話でヒアリングするチャットボット。
2. **LLMノード（意図抽出）**：「駅近で静かな場所」などの曖昧な表現を「徒歩10分以内・幹線道路から離れた住宅街」などの構造化条件に変換。
3. **HTTP Requestノード**：構造化された条件を社内物件DBのAPIに送信し、マッチ物件一覧を取得。
4. **Knowledge Baseノード**：各エリアの住環境情報（学校区・スーパー距離・騒音レベル）をRAGで登録し、物件説明に補足情報を付与。
5. **LLMノード（提案文生成）**：取得した物件データと顧客の希望をもとに「なぜこの物件があなたに合うか」の提案文を生成。
6. **Human Inputノード**：担当者が提案内容を確認・修正してから顧客に送信するステップを挿入。

## 壁
Chatflowが顧客の「予算は300万くらい」という言葉を月額賃料と解釈すべきか購入価格と解釈すべきか混乱し、高額物件を延々と提案し続けてしまうケースが発生した。顧客の文脈（賃貸か購入かが未確定）を正しく扱えていなかった。

## 解決
Chatflowの序盤に「賃貸をお探しですか？購入をお考えですか？」という明示的なフローを追加し、**セッション変数**に「rental」か「purchase」を格納するステップを設けた。以降の数値解釈はこの変数で分岐させ、予算のスコープを固定した。

## 結果
| 指標 | Before | After |
|------|--------|-------|
| 初回条件ヒアリング時間 | 40分/件 | 8分/件 |
| 問い合わせ→内見転換率 | 18% | 31% |
| 条件未整理による離脱率 | 35% | 14% |
| 1日あたり対応可能件数 | 5件 | 12件 |

## 使ったDify機能
| ノード/機能 | 用途 |
|------------|------|
| Chatflow（LINE連携） | 顧客との自然言語ヒアリング |
| LLMノード（意図抽出） | 曖昧条件の構造化変換 |
| HTTP Requestノード | 社内物件DBへのAPI検索 |
| Knowledge Base（RAG） | エリア住環境情報の補足 |
| LLMノード（提案文生成） | パーソナライズされた提案文作成 |
| Human Inputノード | 担当者による確認・承認ステップ |
| セッション変数 | 賃貸/購入フラグの保持 |

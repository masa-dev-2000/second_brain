# ストーリー1：「工場マニュアルBot」
副題 ── 田中係長と設備トラブルの夜間対応 ──

## 登場人物
田中 誠一（47歳）。大手自動車部品メーカーの製造部・設備管理係長。20年以上現場一筋で働いてきたベテランだが、PC操作は苦手。夜勤担当のオペレーターから毎晩のように電話がかかってきて、睡眠不足が続いていた。

## 問題
工場には300台以上の製造設備があり、各設備のマニュアルはPDF・紙・ExcelがSharePoint上に雑然と保管されていた。夜間トラブル時にオペレーターが正しい手順書を探し出すのに平均12分かかっており、月に約40件の問い合わせ電話が田中係長のもとに届いていた。マニュアルの総ページ数は8,000ページを超え、新人は特に途方に暮れていた。

## 出会い
社内のIT推進担当から「Difyというツールで社内文書をチャットで検索できるらしい」と声をかけられた田中係長。「プログラムは書けないけど、ノーコードでできるなら」と週末に触り始めた。

## 実装
1. **Knowledge Baseノード**：全8,000ページのPDFマニュアルをDifyのKnowledge Baseにアップロード。チャンク設定をParent-Child方式にして文脈を保持。
2. **LLMノード**：GPT-4oを接続し、設備番号・エラーコード・症状を受け取って該当手順を回答するプロンプトを設定。
3. **Chatflowアプリ**：「設備番号は？」「エラーコードは？」と順番に聞くフォームフローを組み、不慣れなオペレーターでも使えるUIに。
4. **HTTP Requestノード**：回答に参照マニュアルのページ番号を付与し、SharePointのURLリンクも自動生成。

## 壁
Knowledge Baseに登録した後、「プレスB-07のオイル漏れ」と質問すると、全く関係のない旋盤マニュアルの一節が返ってきた。チャンクサイズが大きすぎてベクトル検索の精度が落ちていたのが原因だった。

## 解決
チャンク設定を「最大512トークン・オーバーラップ50トークン」に変更し、さらにメタデータに設備番号と設備カテゴリを付与して**メタデータフィルタリング**を有効化。設備番号を先に入力させるChatflowの設計も活きた。

## 結果
| 指標 | Before | After |
|------|--------|-------|
| 夜間問い合わせ電話 | 月40件 | 月6件（85%減） |
| マニュアル検索時間 | 平均12分 | 平均1.5分 |
| 田中係長の夜間起床 | 月15〜20回 | 月2〜3回 |
| 新人の独立対応率 | 30% | 78% |

## 使ったDify機能
| ノード/機能 | 用途 |
|------------|------|
| Knowledge Base（RAG） | 8,000ページのPDFマニュアル格納・検索 |
| Chatflow | 設備番号→エラーコード→症状の順序入力UI |
| LLMノード（GPT-4o） | 手順の自然言語回答生成 |
| メタデータフィルタリング | 設備番号で検索範囲を絞り込み |
| HTTP Requestノード | SharePoint URLの動的生成 |

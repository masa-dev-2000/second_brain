# ストーリー9：「サーバー監視の番人」
副題 ── 渡辺 剛、アラート疲れを終わらせた話 ──

## 登場人物
渡辺 剛（わたなべ つよし）・43歳・中規模ECサイトのインフラエンジニア。  
AWS上で30台以上のEC2インスタンスを管理している。  
監視ツールからのアラートが多すぎて「オオカミが来た」状態になっており、  
重要な本物の異常に気づくのが遅れることが問題になっていた。

## 問題
CloudWatch から1日平均150件のアラートが発生していたが、  
真の異常（対応が必要なもの）は平均5件以下だった。  
残りの145件はノイズだが無視できないため、深夜でも確認が必要だった。  
月に1〜2回「夜中3時に起こされる」状況が続き、睡眠負債が蓄積していた。

## 出会い
社内のSlackで同僚が「OpenClaw にインフラの番人をやらせている」という話を共有した。  
「アラートのトリアージをAIがやってくれるって聞いて、すがる思いで試した」

## 実装
```bash
openclaw onboard
# AWS CLI + Slack + PagerDuty 統合
```

```markdown
# SOUL.md（インフラ監視エージェント）
あなたはAWSインフラの監視エージェントです。

CloudWatchアラートを受信したら：
1. 過去30日の同一インスタンスでの同様アラート履歴を確認する
2. 現在のCPU/メモリ/ディスク使用率をAWS CLIで取得する
3. 以下の基準で重要度を判断する：
   - 「緊急」：売上に直結するEC/決済サービスの異常
   - 「警告」：その他のサービスの異常（30分以内に確認が必要）
   - 「情報」：過去に繰り返し発生している既知の一時的な変動
4. 「緊急」のみPagerDutyで渡辺に電話通知する
5. 「警告」はSlackに詳細を投稿する
6. 「情報」は朝8時のデイリーサマリーにまとめて報告する
```

## 壁
「情報」に分類されたアラートの中に、本来「警告」にすべき新種のパターンが紛れ込んでいた。  
ある夜、特定のインスタンスで断続的なメモリスパイクが「既知パターン」と誤判定され、  
翌朝には実際にOOMでインスタンスがクラッシュしていた。  
「AIを信用しすぎた」と剛は反省した。

## 解決
「初めて観測されるパターンは重要度を1段階上げて分類する」というルールを追加した。  
また「同じインスタンスで3回以上『情報』が続いたら『警告』にエスカレーション」という  
頻度ベースのルールも追加し、繰り返しの見落としを防いだ。

## 結果

| 指標 | Before | After |
|------|--------|-------|
| 1日のアラート件数（通知される量） | 150件 | 約8件（緊急・警告のみ） |
| 深夜起床回数 | 月1〜2回 | 月0回（3ヶ月連続） |
| 本物の異常に気づくまでの時間 | 平均2時間 | 平均12分 |
| インシデント対応時間 | 平均45分 | 平均20分（コンテキスト付きで通知されるため） |

「夜ちゃんと眠れるようになった。これだけでQOLが劇的に上がった」

## 使った機能

| 機能 | 用途 |
|------|------|
| AWS CLI 統合 | インスタンスメトリクスの取得 |
| PagerDuty 統合 | 緊急アラートの電話通知 |
| Slack 統合 | 警告・デイリーサマリーの配信 |
| 永続メモリ | アラート履歴と既知パターンの記録 |
| SOUL.md 重要度ルール | トリアージ基準の定義 |

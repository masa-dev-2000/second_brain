# ストーリー8：「問い合わせを捌き切る」
副題 ── 中山由美と、Webフォームとチケットの混沌 ──

## 登場人物
中山 由美（なかやま ゆみ）、33歳。SaaS企業のカスタマーサポートリーダー。  
8名のチームで月間約900件の問い合わせに対応。チケット管理ツールはZendesk。  
問い合わせ経路はWebフォーム・メール・Slackの顧客チャンネルと3つあり、どれも人力でZendeskに転記していた。

## 問題
月900件のうち、Webフォームからの転記作業に1日あたり約45分かかっていた（月で約16時間）。  
「未対応チケットがあると気づかない」問題が月4〜5件あり、SLA（24時間以内返信）違反が月に8件発生。  
問い合わせカテゴリ（技術的問題・請求・操作方法・クレーム）の仕分けが属人的で、ベテランが不在の日は新人が判断に迷い初回返信が遅れていた。

## 出会い
Zendeskの公式ブログで「n8nはZendesk APIとの連携が公式サポートされている」という記事を発見。由美は即座に上長に「2週間で試作します」とプレゼンした。

## 実装
```
【Webフォーム → Zendesk 自動チケット作成】
[Webhook Trigger] Webフォーム送信を受信
    ↓
[OpenAI] 問い合わせ内容を分析：
    「カテゴリを技術/請求/操作/クレームで分類し
    優先度をhigh/normal/lowで判定してください」
    ↓
[Zendesk] チケット作成（カテゴリ・優先度・タグを自動設定）
    ↓
[IF] 優先度 = high ?
    ↓ YES
[Slack] #support-urgentに即時通知
    ↓
[Gmail / Zendesk] 顧客への自動受付確認メール送信

【メール → Zendesk 転記フロー】
[Gmail Trigger] support@ドメイン宛メール受信
    ↓
[OpenAI] 同様にカテゴリ・優先度分類
    ↓
[Zendesk] チケット作成（メールスレッドを紐付け）

【SLA監視フロー】
[Schedule Trigger] 1時間ごと
    ↓
[Zendesk] ステータス=open かつ
    作成から20時間超のチケット取得
    ↓
[IF] 該当あり？
    ↓
[Slack] 担当者にDM警告「SLA違反まであと4時間」
```

## 壁
OpenAIのAPIレスポンスが想定したJSON形式を返さないケースが1日に3〜5件あり、その後の `Zendesk` ノードでエラーが発生してチケット作成が失敗した。本番稼働初日に27件の問い合わせが未チケット化されるという事故が起きた。

## 解決
OpenAIノードの後に `Code（JavaScript）` ノードを追加し、レスポンスのパースに失敗した場合はデフォルト値（カテゴリ: "未分類"、優先度: "normal"）を適用するフォールバック処理を実装。加えてエラー時に由美へSlack DM通知するエラーハンドリングフローをサブワークフローとして追加した。

## 結果
| 指標 | Before | After |
|------|--------|-------|
| フォーム転記作業（月） | 約16時間 | 0時間 |
| SLA違反件数（月） | 8件 | 1件以下 |
| カテゴリ仕分け精度 | 担当者依存 | 約92%（AI分類） |
| 初回返信速度（平均） | 8.4時間 | 3.1時間 |

## 使ったn8nノード・機能
| ノード/機能 | 用途 |
|-----------|------|
| Webhook Trigger | Webフォーム送信の受信 |
| Gmail Trigger | メール問い合わせの受信 |
| OpenAI | カテゴリ分類・優先度判定 |
| Zendesk | チケット作成・管理 |
| IF | 優先度による分岐 |
| Slack | 緊急通知・SLAアラート・DM |
| Schedule Trigger | 1時間ごとのSLA監視 |
| Code（JavaScript） | OpenAIレスポンスのフォールバック処理 |
| Error Trigger | エラー時の通知サブワークフロー |

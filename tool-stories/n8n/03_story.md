# ストーリー3：「履歴書の山を崩せ」
副題 ── 小林奈々と、採用スクリーニングの沼 ──

## 登場人物
小林 奈々（こばやし なな）、38歳。SaaS企業の人事責任者。  
エンジニア・セールス・カスタマーサクセス合わせて年間50名採用が目標。  
採用管理ツール（Recruit Now経由）で週に100〜150件の応募が届き、一人でスクリーニングを担当している。

## 問題
週150件の応募のうち「書類通過」は平均12件（8%）。残り88%の不通過者への一次返信だけで週に約6時間を費やしていた。  
さらに「スキルシートが届いていない」「職務経歴書が読めない形式」など不備対応も週15件ほど発生。  
一次面接のスケジュール調整は候補者・面接官双方へのメール往復が平均4.2往復かかっていた。

## 出会い
採用担当者向けのSlackコミュニティで「n8nとGPTで履歴書スコアリングしてる」という投稿を見た。  
「AIに読ませればいいんだ」という発想がなかった奈々は、すぐに試作を始めた。

## 実装
```
[Gmail Trigger] 応募メール受信（件名に"応募"含む）
    ↓
[Google Drive] 添付ファイル（PDF）をDriveに保存
    ↓
[HTTP Request] Google Document AI でPDF→テキスト変換
    ↓
[OpenAI / GPT-4o] プロンプト：「以下の職務経歴書を読み、
    ・希望ポジションへの適合度（0-100点）
    ・必須スキルの充足率
    ・懸念点
    を JSON で返してください」
    ↓
[IF] 適合度スコア >= 65 ?
    ↓ YES               ↓ NO
[Notion]             [Gmail]
候補者DBに           不通過メール送信
レコード追加          （テンプレート）
    ↓
[Slack] #採用チャンネルへ
スコアと要約を通知
    ↓
[Calendly] 面接候補日時のリンクを自動送付
```

## 壁
PDFのレイアウトが複雑（表組みや写真入り）な場合、OCRの精度が低く、GPTへ渡すテキストがゴミになる問題が発生。スコアが低すぎる誤判定が初週だけで23件あった。

## 解決
Google Document AI の代わりに `pdf-parse` を使うLambdaをHTTP Requestで呼び出す方式に変更し、テキスト抽出の精度を向上。加えてGPTプロンプトに「テキストが読めない場合は score: -1 を返す」という指示を追加し、-1の場合は奈々に手動確認を促す分岐を設けた。

## 結果
| 指標 | Before | After |
|------|--------|-------|
| 一次スクリーニング時間（週） | 約6時間 | 約1時間（例外対応のみ） |
| 不備対応メール（週） | 15件 | 5件（AIが不備検出して自動通知） |
| 面接調整の往復回数 | 平均4.2往復 | 1往復（Calendlyリンクで即完結） |
| 候補者への初回返信速度 | 平均3日 | 2時間以内 |

## 使ったn8nノード・機能
| ノード/機能 | 用途 |
|-----------|------|
| Gmail Trigger | 応募メール受信 |
| Google Drive | PDF添付ファイルの保存 |
| HTTP Request | Document AI / OCR API呼び出し |
| OpenAI | 履歴書のスコアリング・要約 |
| IF | スコア閾値による合否分岐 |
| Notion | 候補者データベース管理 |
| Slack | 採用チームへの通知 |
| Gmail（アクション） | テンプレートメール送信 |

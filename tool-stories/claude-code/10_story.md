# ストーリー10：「3人でリリースする」
副題 ── 藤田奈々と小さなチームの自動化革命 ──

## 登場人物
藤田奈々・31歳・エンジニアリングマネージャー（SaaS スタートアップ）。
エンジニアは自分を含めて3人。全員がプロダクト開発と運用を兼任しており、リリース作業に使える時間が慢性的に不足していた。

## 問題
リリース作業が毎回4〜5時間かかっていた。手順書通りにやっても抜け漏れが出る。先月は CHANGELOG を更新し忘れてクライアントから問い合わせが来た。その前の月はデプロイ後にバージョン番号のタグ付けを忘れた。「3人でやるには作業が多すぎる」と藤田は毎回感じていた。具体的にはリリースノート作成・バージョンバンプ・CHANGELOG 更新・Slack 告知・本番デプロイ・Notion ドキュメント更新の6タスクが毎回存在していた。

## 出会い
「GitHub Actions × Claude Code で release を自動化した」という事例を読んだ藤田が、まず CHANGELOG の自動生成から試してみた。

## 実装
```bash
# リリースノート自動生成
$ claude "main ブランチへのマージコミットから
  今週のリリースノートを生成して。
  機能追加・バグ修正・改善に分類して日本語で書いて"

# GitHub Actions ワークフロー作成
$ claude "git tag を打ったら自動で以下を実行する
  GitHub Actions を書いて：
  1. バージョンバンプ
  2. CHANGELOG 更新
  3. リリースノート生成
  4. Slack #リリース チャンネルに通知
  5. 本番 Heroku にデプロイ"

# テスト・確認
$ claude "このワークフローのドライランテストを書いて。
  本番デプロイだけはスキップして動作確認できるようにして"
```

Claude は既存の commit message の規則（`feat:` / `fix:` / `chore:` プレフィックス）を読み取り、Conventional Commits 形式に沿ったリリースノート生成ロジックを組み込んだ。

## 壁
Slack 通知ステップで、デプロイが失敗したときも「リリース完了」の通知が飛んでしまう不具合が発生した。ステップの成否を確認する条件分岐が抜けていた。さらに Heroku のデプロイ完了を待たずに Slack 通知が送信されていた。

## 解決
「デプロイ完了を確認してから通知する。失敗時は別メッセージを飛ばす条件分岐を追加して」と修正指示。Claude は `if: success()` / `if: failure()` の分岐と、Heroku のヘルスチェック URL をポーリングする待機ステップを追加した。

## 結果
| 指標 | Before | After |
|------|--------|-------|
| リリース作業時間 | 4〜5時間 | 15分（確認のみ） |
| 手動ステップ数 | 18ステップ | 3ステップ |
| 抜け漏れ発生 | 月1〜2件 | 3ヶ月連続ゼロ |
| リリース頻度 | 週1回 | 週3〜4回に増加 |

## 使った機能
| 機能 | 用途 |
|------|------|
| commit 解析・リリースノート生成 | Conventional Commits からの自動生成 |
| GitHub Actions 作成 | リリースパイプライン構築 |
| Slack Webhook 連携 | 成功/失敗の条件付き通知 |
| Heroku ヘルスチェック | デプロイ完了確認 |

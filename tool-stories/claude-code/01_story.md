# ストーリー1：「巨大コードの整理」
副題 ── 田中誠司とレガシー Python の格闘 ──

## 登場人物
田中誠司・38歳・バックエンドエンジニア（SIer 勤務9年目）。
大手物流会社の社内システム開発チームに所属。保守担当になって3年、誰も触りたがらない 2007 年製 Python 2 コードベースを抱えている。

## 問題
担当システムの中核モジュール `order_processor.py` は 210 行の巨大関数1本に全ロジックが詰め込まれており、循環的複雑度は 16。変更するたびにバグが出るため、四半期に1件程度しか機能追加できない状態が続いていた。新しい要件（消費税率の動的切り替え）が降ってきたが、テストカバレッジは 12% しかない。

## 出会い
チームの後輩が「Claude Code 使ってみましょうよ」と提案。田中は懐疑的だったが、「最悪ブランチを捨てればいい」と試してみることにした。

## 実装
```bash
# まず現状を把握させる
$ claude "order_processor.py の main_process 関数の依存関係を
  マップして、リファクタリングのリスク箇所を教えて"

# 特性テストを先に生成
$ claude "現在の振る舞いをロックするための
  characterization test を pytest で書いて"

# 段階的リファクタリング
$ claude "tax_calculation ロジックだけを TaxCalculator クラスに
  抽出して。既存テストが全部通ることを確認しながらやって"
```

Claude はまず関数の依存グラフを Mermaid 形式で出力し、「ここを触るとここが壊れる」という地雷マップを作った。次にテストを 47 件生成してからリファクタリングを開始した。

## 壁
3回目のリファクタリングで、Claude が生成したコードがテストを通過したにもかかわらず、ステージング環境で消費税の丸め処理が 1 円ずれるバグが発覚した。Claude が見落としていた `Decimal` と `float` の混在が原因だった。

## 解決
田中がエラーメッセージを貼り付けて「このバグの根本原因を探して、同じパターンが他にないか全コードを検索して」と指示。Claude は `grep` で同様の `float` 混在を8箇所特定し、一括修正した。

## 結果
| 指標 | Before | After |
|------|--------|-------|
| 循環的複雑度 | 16 | 4〜6 |
| テストカバレッジ | 12% | 78% |
| 関数の行数 | 210行 | 28行（最大） |
| 機能追加リードタイム | 3週間 | 3日 |
| 作業時間（見積もり） | 40h | 18h |

## 使った機能
| 機能 | 用途 |
|------|------|
| コード解析・依存グラフ生成 | リファクタリング前の地雷確認 |
| テスト自動生成 | 特性テストで振る舞いをロック |
| 段階的リファクタリング | 関数抽出・クラス分割 |
| grep によるパターン検索 | 同種バグの横断チェック |

# ストーリー5：「ドキュメントという名の負債」
副題 ── 松本優子と「誰も書かなかった」API仕様書 ──

## 登場人物
松本優子・30歳・テックリード（フィンテックスタートアップ勤務）。
開発速度を優先してきた結果、社内 API のドキュメントはほぼ存在しない状態。新しく入ったメンバーの立ち上がりに毎回2〜3週間かかっており、先月は新人が古い仕様を元に実装してリリース後に不具合が出た。

## 問題
REST API のエンドポイントが約 120 件あるが、OpenAPI 仕様書は 15 件しか整備されていない。残り 105 件はコードを読んで推測するしかなく、フロントエンドチームから「何度も同じことを聞かせないでほしい」とクレームが来ていた。ドキュメント整備に専任を置く余裕はなく、全員が手動で書くと見積もり 80 時間かかる計算になった。

## 出会い
GitHub Actions × Claude Code でドキュメント自動生成を実現したブログ記事を読み、まず手元で試してみることにした。

## 実装
```bash
# Express ルーターを読み込んでスキャン
$ claude "src/routes/ 以下の全 Express ルートを解析して、
  OpenAPI 3.0 形式の YAML を生成して。
  リクエスト/レスポンスのスキーマは型定義ファイルから推測して"

# JSDoc コメント生成
$ claude "各コントローラー関数に JSDoc コメントを追加して。
  パラメータ・戻り値・エラーケースを含めて"

# 変更検知の自動化
$ claude "PR がマージされたとき自動でドキュメントを更新する
  GitHub Actions ワークフローを書いて"
```

Claude はルーターファイルを走査し、型定義・バリデーション・エラーハンドラーを組み合わせてエンドポイントごとの仕様を推測し、OpenAPI YAML を生成した。

## 壁
一部のエンドポイントで、同じ URL パスでも認証状態によってレスポンスのスキーマが変わるものがあった。Claude が生成した仕様書ではそのバリアントが1種類しか記述されておらず、フロントエンドチームが「仕様書と違う」と報告してきた。

## 解決
「認証状態で分岐しているエンドポイントを特定して、それぞれの場合のレスポンス差分を oneOf で記述して」と追加指示。Claude は `req.user` の有無で分岐しているコードを検出し、認証済み/未認証の両スキーマを正確に記述した。

## 結果
| 指標 | Before | After |
|------|--------|-------|
| ドキュメント整備済み | 15件（12.5%） | 118件（98.3%） |
| 新メンバー立ち上がり | 2〜3週間 | 4〜5日 |
| フロントエンドへの口頭質問 | 週10件以上 | 週2件以下 |
| 作業時間（実績） | 推定80h → 実際 12h | — |

## 使った機能
| 機能 | 用途 |
|------|------|
| ルーター・型定義解析 | API スキーマの自動推測 |
| OpenAPI YAML 生成 | 仕様書の自動出力 |
| JSDoc コメント追加 | コードへのインラインドキュメント |
| GitHub Actions 連携 | PR マージ時の自動更新 |

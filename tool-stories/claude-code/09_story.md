# ストーリー9：「0.3秒を削る戦い」
副題 ── 渡辺圭介とAPIレスポンスタイム改善の記録 ──

## 登場人物
渡辺圭介・36歳・バックエンドエンジニア（SaaS 企業勤務）。
PostgreSQL と Python が得意。「コードは書けるが、パフォーマンスチューニングは経験値が必要で苦手意識がある」と感じていた。

## 問題
ユーザー管理画面の「レポート一覧 API」のレスポンスタイムが平均 1,200ms で、SLA（500ms 以下）を大きく超過していた。特に企業アカウント（データ件数が多い）からの問い合わせが急増。DB のクエリは7本走っており、どれがボトルネックかも把握できていない状態だった。

## 出会い
「SQL のチューニングって Claude に聞いたらどうにかなるの？」と同僚に聞いたところ「なるよ」と即答され、半信半疑で試してみた。

## 実装
```bash
# プロファイリングから始める
$ claude "この API エンドポイントのコードを見て、
  パフォーマンスの問題がありそうな箇所を教えて"

# SQL の最適化
$ claude "この SQL クエリの EXPLAIN ANALYZE の結果を見て、
  インデックスの追加・クエリの書き換えを提案して"

# N+1 問題の修正
$ claude "ループ内で DB クエリが走っている N+1 問題を
  特定して、一括取得に書き直して"
```

Claude はコードを読んで「ループの中で `SELECT * FROM reports WHERE user_id = ?` が1ユーザーにつき1回発行されており、100ユーザーなら100クエリになる N+1 が主因」と即座に診断。`EXPLAIN ANALYZE` の結果からインデックスが抜けているカラムも3つ特定した。

## 壁
Claude が提案したインデックスを全部追加したところ、書き込み（INSERT/UPDATE）が逆に 40% 遅くなってしまった。インデックスの多用が書き込みのオーバーヘッドになるという副作用を事前に把握できていなかった。

## 解決
「インデックスを追加したら書き込みが遅くなった。どのインデックスが効果的でどれが不要か判断して」と相談すると、Claude は読み取り頻度と書き込み頻度のトレードオフを分析し、「3つ追加したうち2つは維持、1つは削除」という判断基準を提示した。

## 結果
| 指標 | Before | After |
|------|--------|-------|
| レスポンスタイム（平均） | 1,200ms | 280ms |
| 発行クエリ数 | 7本 | 2本 |
| N+1 問題 | 4箇所 | 0箇所 |
| SLA 達成率 | 23% | 98% |
| チューニング作業時間 | — | 2日（以前なら1週間見込み） |

## 使った機能
| 機能 | 用途 |
|------|------|
| コード静的解析 | パフォーマンスボトルネック特定 |
| EXPLAIN ANALYZE 解釈 | インデックス最適化 |
| N+1 検出・修正 | クエリ数削減 |
| トレードオフ分析 | インデックス取捨選択の判断 |

Story 01

「誰に聞けばいい？」がなくなった日

── 田中麻衣と社内ナレッジの迷宮 ──
👩‍💼

田中麻衣、34歳

SaaS企業の人事・総務リーダー。社員240名。入社してくる人が毎月5〜8名いる。
「経費精算のルールどこ？」「有給の申請ってどうするの？」同じ質問が毎日届く。

問題

田中のSlackには毎日20〜30件の質問が飛んでくる。

「育児休暇の取得要件ってどこに書いてありますか？」
「在宅勤務の際のセキュリティポリシー、最新版はどれ？」
「交通費の上限ってたしか変わりましたよね？」

全部、どこかに書いてある。社内Wikiに、Confluenceに、古いPDFに。
問題は「どこにあるかを知っているのが田中だけ」ということだった。

状況内容
社内規程ドキュメント87ファイル（更新日がバラバラ）
田中への質問数1日平均25件
回答にかかる時間1件3〜8分（ドキュメントを探す時間込み）
本来やりたい仕事採用・研修・エンゲージメント施策

Difyと出会う

社内のエンジニアが「Difyって知ってる？ ドキュメント突っ込むと質問に答えてくれるやつ」と言ったのが始まりだった。

田中はプログラムを書いたことがない。でも試してみた。

実装：ナレッジベースを作る

DifyのKnowledgeタブを開き、「社内規程」ナレッジベースを作成した。

ドラッグ&ドロップしたもの：
✓ 就業規則.pdf
✓ 経費精算ガイド_2025年度版.docx
✓ 育児・介護休業規程.pdf
✓ テレワーク規程.pdf
✓ セキュリティポリシー.pdf
✓ 福利厚生一覧.xlsx → CSV変換
...計31ファイル

チャンク戦略：Q&A方式（よくある質問の形に分割）
検索方式：ハイブリッド（語句の完全一致も拾えるように）

Chatbotをデプロイする

「Chatbot」アプリを作成。Knowledge Retrievalノードと LLMノードを繋いで、プロンプトを書いた：

あなたは「タムラ精工の人事アシスタント」です。
社員からの質問に社内規程を根拠として回答してください。

ルール：
- 回答の末尾に「根拠：{出典ドキュメント名}」を必ず書く
- 規程に書かれていないことは「規程に記載がありません。
  人事部（mai.tanaka@）にご確認ください」と答える
- 古い情報を断言しない

最初の壁

テストしていると、問題が出た。

Q：「交通費の上限はいくらですか？」
A：「月額50,000円です。（根拠：交通費規程2022年版）」

→ 実際は2024年に70,000円に改定されていた。古いPDFを読んでいた。

原因：古いバージョンのPDFも誤ってアップロードしていた。
対処：ナレッジベースから古いファイルを削除し、各ドキュメントに「有効期限」をメモとして追加。プロンプトに「最新日付のものを優先せよ」を追加。

学び： AIは「どれが最新か」を自動判断しない。ドキュメント管理の責任は人間にある。

Human Inputノードを追加する

懲戒・解雇・給与変更に関わる質問は、AIが直接答えるのは危険だと判断した。

フローを改修：Question Classifierで「センシティブな質問」を検出 → Human Inputノードで田中に確認を回す。それ以外は自動応答。

センシティブ判定のキーワード例：
「懲戒」「解雇」「降給」「内部告発」「ハラスメント」
「労働基準監督署」「訴訟」「弁護士」

2ヶ月後

効果

82%
質問の自動解決率
−4.2h
田中の毎日の時間
97%
回答の根拠明示率
0件
センシティブ案件の誤自動回答
「『誰に聞けばいい？』という質問が消えた。
次は『どう制度を改善するか』を考える時間ができた」

Story 02

提案書が、3日から3時間になった

── 井上健太と営業の非効率 ──
👨‍💼

井上健太、28歳

ITコンサル会社の営業。月に10〜15社の提案書を作る。
提案書1本に平均2日半。スライド30枚、見積もり付き。毎回ゼロから書いている。

問題

提案書を書く時間が長すぎた。

フェーズ時間
ヒアリングシートの整理2時間
類似案件の資料を探す3時間
提案書の骨格を書く4時間
見積もりの計算・表作成3時間
上司レビュー対応・修正3時間
合計約15時間

月15本作ると、225時間が提案書だけに消える。月の稼働時間の半分以上だ。

設計：どこを自動化するか

井上は考えた。全部AIに任せるのではなく、「自分が考えるべき部分」と「コピペ作業な部分」を分ける。

自分がやること：ヒアリング、課題の理解、最終判断
AIに任せること：
  - ヒアリング内容から提案骨格の生成
  - 過去案件から類似実績の抽出
  - 工数・見積もり表の計算
  - 提案書Markdownの初稿作成

ワークフローを組む

Difyで「Workflow」アプリを作成した。

INPUT： ヒアリングシート（テキスト貼り付け）+ 顧客業種 + 予算感

【ノード構成】

START
  └→ LLMノード①「課題分析」
        顧客の課題を5点に整理する
  └→ Knowledge Retrieval「類似案件検索」
        過去30件の実績ナレッジから最類似案件を3件取得
  └→ Iterationノード「提案要素生成」
        課題5点それぞれに対して：
          └→ LLMノード「解決策生成」（並列×5）
  └→ HTTP Requestノード「見積もりAPI」
        社内の工数計算APIを叩く
  └→ LLMノード②「提案書Markdown生成」
        全情報を統合して30枚分の初稿を生成
  └→ Human Inputノード「上司確認」
        ⚠ 提案金額が500万円超の場合のみ発動
  └→ END（Markdown出力）

Iterationノードとの格闘

最初に詰まったのがIterationノードだった。

問題： 課題5点を並列処理しようとしたが、Iterationノードが3つ目で止まる。
Difyの既知バグ（ループ変数のリセット問題）。

対処：並列をやめて直列処理に変更。代わりにVariable Aggregatorノードで5つの結果をまとめる。速度は落ちたが安定した。

学び： ループ系ノードは2026年5月時点でバグあり。大事なフローには使わない方が安全。

見積もりAPIの連携

社内の工数計算システム（Excel + VBA）にはAPIがなかった。
エンジニアに頼んで、シンプルなREST APIを1日で作ってもらった。

POST /api/estimate
{
  "project_type": "ECサイト構築",
  "requirements": ["決済機能", "在庫管理", "多言語対応"],
  "deadline_weeks": 12
}

→ {"man_months": 8.5, "cost_range": {"min": 4250000, "max": 5100000}}

このAPIをDifyのHTTP Requestノードから叩くだけで、見積もりが提案書に自動で入る。

3ヶ月後

効果

15h→3h
提案書1本にかかる時間
+6本/月
提案書の増加数
+31%
受注率（上司談）

受注率が上がった理由を上司が分析した。「類似実績が必ず3件入るから、お客さんの安心感が上がってる」。

提案書を書く速度が上がったのではなく、
「考える時間」の割合が増えた。

使ったDify機能

Workflow Knowledge Retrieval ノード Iteration ノード HTTP Request ノード Variable Aggregator Human Input ノード（条件付き） LLM ノード × 複数

Story 03

月曜朝9時、競合レポートが届いていた

── 橘沙織と情報収集の終わりなき戦い ──
👩‍💻

橘沙織、31歳

SaaS企業のマーケティングマネージャー。毎週月曜の経営会議で「競合動向レポート」を出す義務がある。
競合は8社。毎週金曜の午後を、サイトとSNSのチェックに使っていた。

問題

毎週金曜の午後2時間を「競合監視」が占領していた。

確認するもの（毎週）：
- 競合8社のブログ・プレスリリース（新記事チェック）
- 競合8社のTwitter/LinkedIn（週間投稿サマリー）
- G2・Capterra・Review.io（新レビューの確認）
- 競合の料金ページ（価格変更のチェック）
- 自社キーワードのSEO順位変動

→ 全部手作業。漏れも多い。

設計

DifyのTriggerノード（v1.14〜）を使えば、スケジュールで自動実行できる。

毎週日曜22:00に自動起動
  ↓
【Iteration】競合8社をループ
  └→ HTTP Requestノード：各社ブログのRSS取得
  └→ HTTP Requestノード：Twitter API（週間投稿取得）
  └→ HTTP Requestノード：G2レビューページ取得
  └→ LLMノード：「今週の動向を3行でまとめて」
  ↓
【Conditionノード】重要度判定
  └→ 「価格変更」「新機能」「資金調達」を含む → HIGH
  └→ それ以外 → NORMAL
  ↓
LLMノード：週次レポートMarkdown生成
  ↓
HTTP Requestノード：SlackのIncoming WebhookへPOST
  └→ HIGH案件は @channel 付きで即時通知
  └→ NOMALはレポートにまとめて月曜9時配信

壁：Webスクレイピングの制限

HTTP Requestノードでブログを取得しようとしたが、JavaScriptで動的レンダリングするサイトはHTMLが取れなかった。

問題： 競合8社中5社のブログがSPA（React/Next.js）。HTTP Requestでは中身が空のHTMLしか返ってこない。

解決策：RSSが存在する3社はRSSを使用。残り5社はJina AI Reader API（URLを渡すとMarkdown化してくれる無料API）を挟んだ。

GET https://r.jina.ai/https://competitor.com/blog
→ Markdownテキストを返す（JavaScript実行済み）
学び： DifyのHTTP RequestはHTMLを取るだけ。JS描画が必要なサイトには外部のReader APIを挟む。

Conditionノードの精度チューニング

最初、「価格」「新機能」をキーワードでConditionノードに書いたが、誤検知が多かった。

対処：Conditionノードの条件式の代わりに、LLMノードに重要度を0〜5でスコアリングさせ、その数値でConditionを組んだ。

LLMノード出力：
{"importance_score": 4, "reason": "競合Aが価格を20%値下げ"}

Conditionノード：
importance_score >= 4 → HIGH通知
importance_score < 4  → 通常レポートに収録

3ヶ月後

効果

0h
沙織の毎週の情報収集時間
8社→12社
監視対象（追加が楽に）
3件
競合の価格変更を先に把握（対応できた）

「自分で調べていた頃は土日に気づいていた情報を、今は日曜夜に自動でSlackに来る。月曜の会議で僕が一番詳しい人間になれた」と沙織は言った。

収集をやめたのではなく、
収集の主体を「自分」から「システム」に変えた。

使ったDify機能

Trigger ノード（スケジュール起動） Iteration ノード HTTP Request ノード Condition ノード LLM ノード（重要度スコアリング） Slack Webhook 連携

Story 04

0.3秒で分類して、3分で返す

── 小坂雄太とカスタマーサポートの反乱 ──
👨‍🔧

小坂雄太、32歳

アパレルEC「SPOOL」のCSリーダー。チームは自分を含めて3人。1日受信メール約280通。

問題

毎朝9時のメールボックスに「未読 284件」。

メール種別割合処理時間/件
配送状況の問い合わせ38%3分
返品・交換の申請22%8分
サイズ・素材の質問19%5分
クレーム・感情的な内容12%25分
その他9%10分

問題はクレームだった。怒っているメールを読むたびに集中力が削られ、決まった答えがある配送問い合わせを処理していると、本当に頭を使うべきクレーム対応の質が落ちる。

設計思想

「完全自動化」ではなく「人間の判断を最小限のところだけ使う」。クレームだけは人間が書く。それ以外はAIが下書きを作り、人間が承認する。

Chatflowの構成

メール受信（Webhook）
  ↓
Question Classifierノード（5クラス）
  ├─ 配送照会 → 注文API呼び出し → LLM生成 → Human Input
  ├─ 返品申請 → FAQ検索 → LLM生成 → Human Input
  ├─ 商品質問 → Knowledge Retrieval → LLM生成 → Human Input
  ├─ クレーム → Codeノード（緊急度スコア）→ Human Input（担当者直送）
  └─ その他  → FAQ検索 → LLM生成 → Human Input
  ↓
HTTP Requestノード（SendGridでメール送信）

Question Classifierの精度チューニング

最初に詰まったのが分類の精度だった。

誤分類例：
「届いた商品の色が写真と違います。返品したいです」
→ 「商品の質問」に分類（正解は「返品申請」）

クラスの説明文を書き直した：

【修正後のクラス2の説明】
返品・交換を希望している。届いた商品に問題がある。
写真と違う・サイズが合わない・破損していた。
こういった場合はすべてクラス2。
学び： Question Classifierの「ノード」はコードではなくプロンプト。例外ケースを説明文に書くと精度が上がる。

2週目：本番投入結果

初日の実績（267通）

94.1%
分類精度
8.3→1.4分
一人あたり処理時間/通
86.5%
AIの下書きをそのまま承認

本当の変化

3週目に入ったある日、村田が言った。

村田 小坂さん、お客さんへの返信、なんか丁寧になってると思うんですよ
小坂 AIの文章だから？
村田 いや、僕たちの文章が。

以前は配送照会メールを1日90通さばいていたから、後半は雑になっていた。今は確認作業になったので1通1通ちゃんと読んでいる。AIが書いた下書きのトーンを「人間らしいちょうどいい温度感」に修正するうちに、それがプロンプトに蓄積されていった。

Difyが変えたのは、メールの処理速度ではなかった。
チームが何に時間を使うか、だった。

「コードって何ですか？」と聞いた経営者

── 田村悟と、Excelに埋まった3年分の真実 ──
🏭

田村悟、47歳

金属加工の町工場「タムラ精工」の二代目社長。従業員22名。PCは使える。Excelも「まあ使える」と思っている。SUM関数とVLOOKUPは書けた。昔は。

問題

銀行から電話が来た。「過去3年分の月別・製品別の利益率推移を出してほしい」。田村は「わかりました」と答えて電話を切り、デスクの引き出しを開けた。

2023年売上.xlsx
2023年売上（確定版）.xlsx
2023年売上（確定版・修正後）.xlsx
2024年売上_1月.xlsx
...（計23ファイル）

製品コードの表記：
  「A-001」「A001」「製品001」が混在
原価：為替によって月ごとに変動
提出期限：5日後

「3日かかる。いや1週間かも」

息子からのLINE

息子 親父、Claude Code使ってみて。コード書けなくても、ファイル渡すだけで分析してくれるから。インストールだけしといて
田村 コードって何ですか？
息子 とりあえずインストールだけ。あとはしゃべりかけるだけでいいから

最初の5分間

黒い画面が開いた。田村は思い切って打った：

Excelファイルが23個あります。
銀行に出す資料を作りたいです。
月別・製品別の利益率推移のグラフが必要です。
どうすればいいですか？
わかりました。一緒にやりましょう。

まずExcelファイルがどこにあるか教えてください。
全部同じフォルダにありますか？

Claudeが見つけたもの

フォルダパスを伝えて数分後：

23ファイルを確認しました。いくつか問題が見つかりました：

1. 製品コードの表記ゆれ
   「A-001」「A001」「製品001」が同じ製品を指している

2. 原価シートが別ファイル（原価計算_新.xlsx）にある

3. 2024年1月〜3月のファイルに「為替調整」列がない

⚠ 気になる点：
  製品「B-005」の利益率が2024年7月から急落（28%→11%）
  製品「C-012」は売上増加だが利益率が年々低下
  （2022年:22%→2025年:14%）

田村は画面を見て固まった。
C-012は「よく売れる製品」だと思っていた。数字だけ見ていたから、利益率が侵食されていたことを3年間見落としていた。

グラフ作成

銀行に提出するグラフを作ってください。
A4サイズで印刷できる形式で。

5分後、分析レポート.pdfができていた。グラフ6枚、数字が整理されていた。フォントも揃っていて、銀行に出しても恥ずかしくない見た目だった。

翌日：銀行からの追加質問

「2023年度の第3四半期だけ利益率が突出して高いんですが、理由を教えていただけますか？」

2023年7月〜9月の利益率が高い理由を
データから読み取れますか？
確認しました。この期間に2つの要因が重なっています：

1. 「A-003（ステンレスシャフト）」への大口受注
   通常の月の4.2倍の売上
   大口受注は固定費が分散されるため利益率が高くなります

2. 原材料のニッケル価格が前期比12%低下
   （原価計算_新.xlsxのデータより）

銀行への説明文を作りましょうか？
作ってください
